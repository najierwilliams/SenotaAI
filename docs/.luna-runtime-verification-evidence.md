## Official Vercel Queue findings

The [Vercel Queues JavaScript SDK documentation](https://vercel.com/docs/queues/sdk) states that the TypeScript SDK is installed as `@vercel/queue`; producers call `send(topic, payload, options)` and receive a `messageId`; a Node/Express consumer can be built with `QueueClient.handleNodeCallback`; and a push consumer requires an `experimentalTriggers` entry in `vercel.json` using `type: queue/v2beta` and a topic.

The [Vercel Queues concepts documentation](https://vercel.com/docs/queues/concepts) describes durable, at-least-once delivery with retries and visibility timeouts. It says JavaScript/TypeScript push consumers are configured in `vercel.json`, are invoked by Vercel's private queue infrastructure rather than a public route, and require idempotent handling because delivery can occur more than once.

## Official Vercel Workflow findings

The [Vercel Workflows documentation](https://vercel.com/docs/workflows) describes Workflows as a managed durable system built on the `workflow` SDK. It requires a workflow implementation, uses durable workflow runs/steps, and stores event/state information managed by Vercel. The documentation presents `start()` as returning a workflow run when a configured workflow is started.

## Initial repository consequence

At the start of this audit, the repository contained neither `@vercel/queue` nor `workflow`; no `vercel.json` queue trigger; no queue consumer; no workflow source; and no runtime ingress for `executeLunaWorkerStep`. The deployed `LunaDurableRuntime` was `UnavailableLunaDurableRuntime`, whose `dispatch()` returned `accepted: false` and `runId: null`. This made `WAITING_FOR_RUNTIME` factual and fail-closed.

## Official Workflow SDK integration requirement

The official [Workflow SDK Express guide](https://workflow-sdk.dev/docs/getting-started/express) requires `workflow`, `nitro`, and `rollup`; a `nitro.config.ts` using the `workflow/nitro` module; and changing the app build/development path to Nitro. The official [Vite guide](https://workflow-sdk.dev/docs/getting-started/vite) likewise requires `workflow`, `nitro`, the `workflow/vite` and `nitro/vite` plugins, and Nitro API-route handling. In both guides, a workflow uses the `"use workflow"` directive and durable work runs through `start()` from `workflow/api`.

The existing `senota-ai` build is not this shape: it uses Vite to produce the client plus esbuild to bundle `server/_core/index.ts` and `server/vercel-entry.ts` as a normal Express server. Therefore the documented Workflow SDK path is a deliberate build/entrypoint migration, not a drop-in package install.

## Queue integration staged for production validation

The selected Queue path was implemented without replacing Vite or Express: `@vercel/queue` was added; `VercelQueueLunaDurableRuntime` publishes only a bounded `luna_worker_v1` message with an idempotency key; `api/luna/queue-consumer.ts` is declared in `vercel.json` as a private `queue/v2beta` consumer; and the consumer maps provider delivery metadata to existing owner-scoped mission, task, worker, recovery, attention, version, and immutable audit records. It accepts a runtime only when `send()` returns the provider-issued `messageId`; a null identifier, local process, or dispatch failure remains `UNAVAILABLE` or `DEGRADED` with no fabricated run.

The consumer executes no shell command and no external web research. It can currently use only the reviewed, bounded Knowledge Space retrieval and in-process read-only scientific registry adapters. It checks persisted pause/cancel state before a worker step, respects task dependencies, records provider message IDs in immutable activity, uses bounded retry handling, and treats at-least-once redelivery as idempotent. This is **staged source**, not a production-success claim: deployment must still build the private function and the first accepted queue message must return a real provider `messageId` before the console can report a configured durable run.
